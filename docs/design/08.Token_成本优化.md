# 08. Token 成本优化：模型分级、记忆压缩与精准修复

> 状态：已落地（2026-11-09）  
> 适用：UI Graph、Architect Graph、Supervisor 预留能力  
> 目标：在不降低生成质量的前提下，把单次 Run 的 Token 消耗压到可控范围，
> 并消除“重试越多次、上下文越大、成本越高”的正反馈。

---

## 1. 问题与约束

### 1.1 三个成本放大器

| 放大器 | 现状 | 后果 |
|---|---|---|
| 单一模型 | Planner / Coder / Architect 全部使用 `deepseek-chat` | 简单分类任务与复杂代码任务同价同模型 |
| 历史全量回传 | `threadContext.chatHistory`、`previousRuns`、`ui_history` 原样进入 Prompt | 多轮对话线性膨胀，Checkpoint 也随之膨胀 |
| 错误全量回传 | `verify_result.error_logs` 保存并回传完整 `npm run build` stdout | 一次失败就把整份构建日志塞给 Coder，修复成本翻倍 |

### 1.2 非目标

- 不引入微调（SFT / LoRA / RLHF）。
- 不改变 SSE、API、前端可见协议。
- 不牺牲 `retry_count < 3` 的硬上限。
- Supervisor 当前是确定性规则路由，本身 0 Token；本文的 `routing`
  能力位只为未来 LLM 分类器预留。

## 2. 动态模型路由（ModelRouter）

### 2.1 能力分级

`ai_core/model_router.py` 定义 `ModelRouter` 与 `ModelProfile`，按任务能力
选择模型，而不是按调用点硬编码。

| 能力 | 任务 | 默认层级 | 原因 |
|---|---|---|---|
| `routing` | Supervisor 意图分类（预留） | FAST | 短文本分类，规则未命中时才调用 |
| `validation` | 表单 / 契约格式校验（预留） | FAST | 确定性校验优先，模型仅兜底 |
| `summary` | 历史记忆压缩 | FAST | 摘要任务，输入长但输出极短 |
| `planner` | UI Planner | FAST | 输出结构化计划，不需要强推理 |
| `coder` | UI Coder / 复杂 JSX | STRONG | 代码正确性直接决定构建成功率 |
| `architect_analyze` | 应用形态判别 / 澄清问题 | FAST | 分类 + 少量字段抽取 |
| `architect_contract` | 契约起草 / 修订 | STRONG | 长上下文 + 结构化输出，质量要求最高 |

### 2.2 配置优先级

单个任务最终模型按以下顺序解析：

```text
任务级覆盖（MODEL_<TASK>_NAME）
  > 层级模型（MODEL_STRONG_NAME / MODEL_FAST_NAME）
  > DEEPSEEK_MODEL
  > deepseek-chat
```

温度同理：FAST 默认 `0.0`，STRONG 默认 `0.2`，均可通过环境变量覆盖。

### 2.3 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `MODEL_FAST_NAME` | `DEEPSEEK_MODEL` | 快速 / 廉价模型 |
| `MODEL_STRONG_NAME` | `MODEL_FAST_NAME` | 复杂任务模型 |
| `MODEL_FAST_TEMPERATURE` | `0.0` | 分类、摘要、计划 |
| `MODEL_STRONG_TEMPERATURE` | `0.2` | 代码、契约 |
| `MODEL_SUMMARY_NAME` | 空 | 记忆压缩专用覆盖 |
| `MODEL_PLANNER_NAME` | 空 | UI Planner 覆盖 |
| `MODEL_CODER_NAME` | 空 | UI Coder 覆盖 |
| `MODEL_ARCHITECT_ANALYZE_NAME` | 空 | 形态判别覆盖 |
| `MODEL_ARCHITECT_CONTRACT_NAME` | 空 | 契约生成覆盖 |

> 生产建议：`MODEL_FAST_NAME` 使用更低价的模型；`MODEL_STRONG_NAME`
> 保持高质量模型。只在明确需要时使用任务级覆盖。

### 2.4 实现约束

- `DeepSeekAgentLLM` / `DeepSeekArchitectLLM` 内部持有 `ModelRouter`，
  按任务惰性构建并缓存 `ChatOpenAI` 客户端。
- Mock 模式不实例化真实客户端，行为完全离线。
- 路由决策写日志（任务、层级、模型名），便于成本归因。

## 3. 历史记忆压缩（Summarization）

### 3.1 触发条件

在 UI Graph 与 Architect Graph 的第一个节点增加 `summarize_history`，
位于所有业务节点之前：

```text
UI:        START -> summarize_history -> planner -> ...
Architect: START -> summarize_history -> ingest_context -> ...
```

每次从 `START` 进入时执行。节点内部：

1. 汇总当前可见历史：
   - UI：每个标注的 `threadContext.chatHistory` 与 `previousRuns`；
   - Architect：`ui_history`。
2. 用混合估算器计算 Token：CJK 字符约 0.7 token，其余字符约 0.25 token。
3. 超过 `HISTORY_SUMMARY_TOKEN_THRESHOLD`（默认 3000）才压缩。
4. 调用 `summary` 能力的轻量模型，输出不超过
   `HISTORY_SUMMARY_MAX_CHARS`（默认 200 字）的“核心需求与约束”。
5. 用摘要替换原始历史：
   - 保留 `threadContext.historySummary`；
   - `chatHistory` 仅保留一条 `role=system` 的摘要；
   - `previousRuns` 清空。
6. 节点输出 `history_tokens_before` / `history_tokens_after`，用于观测。

### 3.2 失败降级

摘要调用失败、超时或返回空字符串时：

- 记录日志并发出 `node.progress` 提示；
- 保留原始历史，不阻断 Run；
- 下一次进入 `START` 时再次尝试。

### 3.3 与 Checkpointer 的关系

LangGraph 在每个节点边界保存 Checkpoint。`summarize_history` 是首个节点，
因此后续 Checkpoint 只承载压缩后的历史，而不是原始长对话。恢复
（`Command(resume=...)`）时从暂停点继续，不会重复压缩，也不会丢失摘要。

### 3.4 观测字段

| 字段 | 位置 | 说明 |
|---|---|---|
| `history_summary` | AgentState / ArchitectState | 压缩后的摘要 |
| `history_tokens_before` | 同上 | 压缩前估算 Token |
| `history_tokens_after` | 同上 | 压缩后估算 Token |

## 4. 错误日志精准截断（Diff 修复）

### 4.1 提取函数

新增 `ai_core/agent/error_context.py`：

```python
extract_error_context(stderr: str, code: str,
                      context_lines: int = 10,
                      max_chars: int = 2000) -> str
extract_error_fingerprint(stderr: str) -> str
```

### 4.2 处理流程

1. 去除 ANSI 控制字符，统一换行。
2. 按优先级提取错误位置：
   - `src/App.jsx:12:5`；
   - `src/App.jsx (12:5)`；
   - `line 12`。
3. 提取 Error Message：
   - 含 `error / ERROR / failed / ✘ / SyntaxError / ERR_` 的行；
   - 去重、限长 800 字符。
4. 若定位到文件与行号：
   - 只截取报错行前后各 `context_lines`（默认 10）行；
   - 带行号输出，明确标注 `>` 当前行；
   - 总长度受 `max_chars` 限制。
5. 无法定位时：回退为 stderr 末尾 1200 字符，而不是完整 stdout。

### 4.3 注入点

`verifier` 在构建失败时同时产出：

| 字段 | 内容 |
|---|---|
| `error_logs` | 完整日志，仅用于 UI / 审计，不再进入 Prompt |
| `error_context` | 精准截断后的错误 + 代码片段 |
| `error_fingerprint` | 归一化错误指纹 |

`planner` 与 `coder` 只读取 `error_context`；没有时回退到 `error_logs` 的
尾部，而不是全量。这样单次修复的输入从“整份构建日志 + 整文件”降到
“Error Message + 约 20 行代码”。

## 5. 调用深度限制

### 5.1 硬上限

- `AgentGraphRunner._max_retries = min(max(0, max_retries), 3)`；
- Service 初始化状态时 `max_retries = min(request.options.max_retries, 3)`；
- `evaluator` 只在 `retry_count < max_retries` 时调度下一次 Coder。

### 5.2 同错终止

新增 `last_repair_error_fingerprint` 状态：

1. 首次构建失败：计算指纹，调度第 1 次修复，并记录指纹；
2. 第 2 次构建失败：
   - 若指纹与上次相同且 `retry_count >= 1`，直接 `FAILED`，
     `error_code=REPEATED_ERROR`；
   - 指纹不同才继续第 2 次修复。
3. 最多 3 次修复，随后 `error_code=VERIFY_FAILED`。

目的：同一错误反复修复通常意味着模型已无法从现有上下文突破，
继续重试只会线性放大 Token 消耗。

## 6. 成本预估

以单次 Run 为例（估算口径：输入 Token 占主要成本，输出按 1/4 计）：

| 场景 | 优化前 | 优化后 | 降幅 |
|---|---|---|---|
| 首次生成（无历史） | 100% | 100% | 0%（Coder 仍需完整源码） |
| 多轮对话（历史 12k tokens） | 100% | 25% ~ 35% | 65% ~ 75% |
| 一次构建失败 | 100% | 25% ~ 40% | 60% ~ 75% |
| 三次构建失败（重复错误） | 100% | 15% ~ 25% | 75% ~ 85% |
| 混合负载（30% 多轮 + 20% 修复） | 100% | 45% ~ 60% | 40% ~ 55% |

> 实际降幅取决于历史长度、错误日志体积与模型价差。启用
> `MODEL_FAST_NAME` 与 `MODEL_STRONG_NAME` 的价差后，简单任务还可再降。

## 7. 验收

| 项 | 标准 |
|---|---|
| 模型路由 | 任务 → 模型名可通过环境变量改变，单测覆盖优先级 |
| 历史压缩 | 超过阈值才压缩；摘要 ≤200 字；失败降级不阻断 |
| 错误截断 | 只含 Error Message + 前后 10 行代码；无定位时限长回退 |
| 重试上限 | 不超过 3 次；同错第 2 次直接 FAILED |
| 兼容性 | SSE / API / 前端协议不变；Mock 全离线 |
