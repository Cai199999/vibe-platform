# 企业内部安全开发规范与 JWT 鉴权指南

> 文档编号：SEC-2026-001  
> 适用范围：集团总部及各子公司所有对外服务、内部微服务、后台管理系统  
> 生效日期：2026-01-01  
> 归口部门：信息安全部 / 平台架构组

## 一、目的与适用范围

本指南用于统一集团内部 API 的鉴权方式、令牌生命周期、密钥管理、输入校验与敏感数据处理要求。凡接入统一认证中心（IAM）的业务系统，无论使用 Java、Node.js、Python 还是 Go 实现，都必须遵守本指南。新增系统在立项评审阶段即需确认鉴权方案，安全评审未通过不得上线。历史系统应在本指南生效后两个发布周期内完成整改，确实无法按期整改的，需由业务负责人提交风险接受单，并经信息安全部审批。

本指南不替代等保测评、数据分级分类和隐私合规要求。涉及个人敏感信息、支付、医疗、未成年人数据的系统，还必须执行相应的专项规范。本文中的“必须”表示强制要求，“建议”表示除非有充分理由否则应执行。

## 二、API 鉴权方式

公司所有对外开放 API 统一使用 OAuth 2.1 客户端凭证模式（client credentials）。第三方合作方不得使用静态 API Key 直接访问业务接口；合作方需先在 IAM 注册应用，获取 client_id 与 client_secret，通过 `POST /oauth/token` 换取访问令牌。令牌只允许通过 HTTPS 传输，禁止放在 URL 查询参数中，避免被网关日志、浏览器历史和 Referer 泄漏。

公司内部服务之间的调用统一使用 JWT Bearer Token，由统一认证中心（IAM）签发。调用方在请求头中携带 `Authorization: Bearer <access_token>`，被调用方必须校验签名、签发者、受众、过期时间与令牌状态。禁止各业务系统自行实现用户名密码登录后签发“自制 Token”，也禁止使用永久有效的服务令牌。对于高敏感的内部接口，除 JWT 外还应启用 mTLS 双向证书校验，形成“身份令牌 + 传输身份”的双重保障。

后台管理系统的用户登录仍由 IAM 完成，业务系统只保存 IAM 返回的会话标识，不保存用户密码。移动端与桌面端使用 OAuth 2.1 授权码模式配合 PKCE，禁止在客户端内置 client_secret。所有刷新令牌必须绑定设备指纹或会话 ID，用户登出、改密、离职或检测到异常登录时，IAM 会立即吊销对应令牌。

## 三、JWT 令牌规范

JWT 必须使用 RS256 非对称签名，禁止使用 `none` 算法，禁止在生产环境使用 HS256 共享密钥。IAM 通过 JWKS 端点发布公钥，业务系统应缓存公钥并支持 `kid` 轮换，缓存时间不超过 10 分钟。签发者固定为 `https://iam.corp.example.com`，受众必须与当前服务注册的 audience 一致，禁止接受任意 audience 的令牌。

访问令牌（access token）的有效期统一设置为 15 分钟。该时长足以覆盖一次正常的服务调用链，又能把令牌泄漏后的风险窗口控制在可接受范围内。刷新令牌（refresh token）的有效期设置为 7 天，且必须一次性使用；刷新成功后旧刷新令牌立即失效，防止重放。禁止通过延长访问令牌有效期来规避刷新逻辑，确有特殊性能需求的批量任务，应申请独立的服务账号并使用短时令牌。

时钟偏移容忍度统一设置为 60 秒。业务系统校验 `exp`、`nbf`、`iat` 时必须使用统一的时间源，不得依赖本地随意修改的系统时间。令牌中的用户标识使用 `sub`，租户标识使用 `tenant_id`，权限范围使用 `scope`，禁止把手机号、身份证号、密码等敏感信息写入 JWT 载荷，因为 JWT 只是签名而非加密，任何拿到令牌的人都可以读取载荷。

令牌吊销采用“短有效期 + 黑名单”组合策略。用户登出、管理员封禁、检测到令牌泄漏时，IAM 将令牌的 `jti` 写入 Redis 黑名单，黑名单保留时间与令牌剩余有效期一致。业务系统对高风险操作必须查询黑名单；普通只读接口可依赖 15 分钟短有效期，但不得关闭签名与过期校验。

## 四、密钥与配置管理

所有密钥、数据库口令、第三方 API Key 必须通过环境变量或密钥管理服务注入，禁止写入代码仓库、镜像层、前端打包产物和日志。`.env` 仅用于本地开发且必须加入 `.gitignore`；仓库只提交 `.env.example`，其中不得包含真实值。生产环境使用 KMS 托管密钥，应用启动时按最小权限拉取，密钥轮换周期不超过 90 天。

JWT 签名私钥只允许 IAM 持有，业务系统只接触公钥。发现私钥泄漏时，应立即在 IAM 轮换密钥、更新 JWKS、吊销全部在途令牌，并在 30 分钟内完成事件上报。日志中禁止打印完整 Authorization 头、Cookie、密码、验证码和密钥；确需排查时只记录令牌前 8 位与 `jti` 的后 6 位，并进行脱敏。

## 五、输入校验与注入防护

所有外部输入必须在服务端校验，前端校验只用于提升体验，不能作为安全边界。字段长度、类型、枚举范围、文件类型和大小都要有明确上限。数据库访问必须使用 ORM 或参数化查询，严禁把用户输入拼接进 SQL 字符串；动态排序字段必须使用白名单映射，禁止直接把 `orderBy` 参数拼进 `ORDER BY`。调用外部命令时使用参数数组，禁止 `shell=True` 或字符串拼接。

密码必须使用 Bcrypt 哈希存储，cost 因子不低于 12；禁止使用 MD5、SHA1、SHA256 裸哈希或可逆加密保存密码。用户不存在与密码错误应返回相同提示，避免账号枚举。登录、注册、找回密码等接口必须限流，并对连续失败进行渐进式延迟或验证码挑战。文件上传需校验扩展名、MIME 类型和文件头，重命名后存储到非 Web 根目录，禁止执行上传目录中的脚本。

## 六、日志、审计与应急响应

所有鉴权失败、权限拒绝、敏感数据导出、管理员操作必须写入审计日志，包含时间、主体、租户、来源 IP、请求 ID、操作对象和结果。审计日志只追加不可篡改，保留不少于 180 天。应用日志不得记录完整令牌与个人敏感信息；错误响应不得把堆栈、SQL、内网地址返回给客户端。

发现疑似令牌泄漏、越权访问或数据泄露时，应在 15 分钟内启动应急响应：隔离受影响服务、吊销相关令牌、保留现场日志、通知信息安全部，并在 24 小时内提交初步分析报告。任何安全事件都不得私下处理或延迟上报。

## 七、上线检查清单

1. 对外 API 使用 OAuth 2.1 客户端凭证模式，内部服务使用 IAM 签发的 JWT。
2. JWT 使用 RS256，校验签名、iss、aud、exp、nbf，访问令牌 15 分钟，刷新令牌 7 天。
3. 密钥通过环境变量或 KMS 注入，仓库与镜像中无真实密钥。
4. 数据库访问使用 ORM / 参数化查询，排序字段走白名单。
5. 密码使用 Bcrypt cost ≥ 12，登录接口具备限流与失败审计。
6. 日志完成脱敏，审计日志保留 180 天以上。
7. 安全评审、依赖漏洞扫描与渗透测试全部通过后方可上线。
